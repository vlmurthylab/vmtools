# AGENTS.md — vmtools

vmtools is the lab's public R package of tools for cardiometabolic epidemiology: the PREVENT and Pooled Cohort Equations risk scores, insulin sensitivity and resistance indices, GLI spirometry reference equations, and small helpers. Licensed GPL-3.0-only; released on Zenodo.

These rules apply to every AI coding assistant working in this repo: Claude Code (which loads this file through `CLAUDE.md`), Codex and any other. Only the **This project** section at the end is edited per project; the rest is lab policy.

## How this lab works with AI assistants

**AI assistants never run on a machine that can reach the lab's protected data.** That means PHI, and also every other research dataset the lab holds, such as cohort study data (CARDIA, MESA, the Framingham Heart Study and others), which is covered by data use agreements, licenses and IRB protocols even when it is de-identified and not PHI. They work only in cloud sessions on this GitHub repo, which holds code, figures and summary results, never data. GitHub is the bridge:

1. The assistant writes and tests code here, against stand-in data (synthetic or public).
2. A lab member pulls the code onto approved lab storage and runs it on the real data there, without an assistant.
3. The lab member reviews the outputs and commits only aggregate results (summary tables, figures) back to GitHub, checking every file.

**Check before starting any task, before anything else (including turning on the hook below).** If `data/` holds anything other than `README.md` and stand-in files generated by code or downloaded from public sources, a `.env` file exists, `DATA_DIR` is set, or either of the lab's Turbo volumes is mounted or reachable, you may be on a machine with protected data: do nothing else, and tell the user. Both volumes are protected:

| Volume | Holds | Linux (Great Lakes, Armis2) | Windows | Mac |
|---|---|---|---|---|
| `umms-vlmurthy-sn` | PHI (HIPAA-approved) | `/nfs/turbo/umms-vlmurthy-sn` | `\\umms-vlmurthy-win.turbo.storage.umich.edu\umms-vlmurthy-sn` | `/Volumes/umms-vlmurthy-sn` |
| `umms-vlmurthy` | Other research data (data use agreements, licenses) | `/nfs/turbo/umms-vlmurthy` | `\\umms-vlmurthy-win.turbo.storage.umich.edu\umms-vlmurthy` | `/Volumes/umms-vlmurthy` |

On a Mac a volume connected twice may appear as `/Volumes/umms-vlmurthy-1` and so on. To check, look for `umms-vlmurthy` (which matches both volumes) in the output of `mount` (Mac and Linux) or `net use` (Windows), and test whether the paths above exist.

Also stop if the machine is Great Lakes or Armis2, or if a storage path listed under **This project** is reachable.

## Hard rules

- **No subject-level data in the conversation or the repo**, identified or de-identified, from either Turbo volume or any other source covered by a data use agreement or license. **This includes cohort study data** (CARDIA, MESA, the Framingham Heart Study, UK Biobank, BioLINCC and dbGaP datasets, and the like) and credentialed datasets (such as MIMIC), even when de-identified. Public data that anyone can download without an agreement (such as NHANES) is the only exception. This includes pasted text, uploaded files, screenshots (RStudio `View()`, Excel), knitted reports, logs, notebook outputs and error messages from the real run.
- **If data appears anyway, stop.** Don't read further, summarize it or use it, and never quote any of it in replies, commit messages or PR comments: quoting it publishes it again. Tell the user to tell Venk right away. If it was already pushed, deleting the file is not enough, because it stays in git history; Venk decides how to remove it. Don't open or restore data-like files from git history, old commits or PR diffs.
- **Never ask for real data.** Don't ask for rows, `head()` or `summary()` output, or output from the real run. Ask for structure instead: column names and types, the data dictionary, or counts with small cells suppressed. To debug an error from the real run, ask the user to reproduce it on stand-in data, or to send the traceback with all data values removed.
- **Build and test with stand-in data generated at run time.** Write code that creates synthetic data (or downloads public data such as NHANES into `data/`, which git ignores); don't commit stand-in data files, including in `reference/` or `results/tables/`. Synthetic data must never be derived from real rows.
- **Commit only code, figures, summary tables, small reference tables (published coefficients, lookup tables) and docs.** Follow `.gitignore` and the folder rules in the README. Commit notebooks with outputs cleared (for example with `nbstripout`).
- **Small counts:** if the project's data use agreement requires suppressing small cells, set `MIN_CELL` in `phi-guard.conf` to the threshold recorded under **This project** or given by the user; never guess it or lower an existing value. The check only covers count columns (named in `COUNT_COLUMNS`) in `results/tables/`; percentages, HTML reports and figures need a person to look at them.
- **Don't weaken the guard rails.** Don't edit the lab core files (each says so at the top; see the README), the core part of `.gitignore` or of this file (everything above **This project**). In `phi-guard.conf`, you may tighten (add `BLOCK_FILES` entries, set `MIN_CELL` as above) but not loosen (`ALLOW_FILES`, `MAX_TABLE_ROWS`, `ID_COLUMNS`, removing entries). `hooks/pre-commit.local` and other workflows may be changed, but never to skip or weaken a check. Do none of these, and never use or suggest `git commit --no-verify`, unless the PI asked for that specific change in a PR or issue. Use `phi-ok` only when a flagged line is not about a person (a random seed, a published sample size), and say so in the commit message.
- **No secrets or data paths in code.** Code reads the data location and any credentials from a local `.env` file or environment variables (for example `DATA_DIR`) on the lab machine. Writing the storage path in the README for people is fine.
- **Review results coming back.** When a pull request adds results from the real run, check every table and figure for anything individual-level before anything else: single rows, rare categories, small counts, exact dates, and figures that plot individual points or label outliers.

## Running the PHI check

At the start of a session, turn the hook on: `git config core.hooksPath hooks` (from R: `source("tools/install_hooks.R")`). Before each commit run `perl tools/phi_guard.pl --staged`, and before calling a PR ready run `perl tools/phi_guard.pl --all`. GitHub runs the same check on every push. It is a safety net for common patterns, not a substitute for looking.

## Conventions

- Small, focused commits with messages explaining *why*.
- R or Python, written to be read: comment anything non-obvious. Scripts in `code/` should run in order from a clean start.
- Record the versions of packages that affect results (for example, a package's release tag) in the README or with the results.
- Prefer simple, boring solutions.
- **Before calling a pull request ready to merge:**
  1. Bring in `main` if it has moved and resolve conflicts.
  2. Read and address every PR comment and review thread.
  3. Run the checks: `perl tools/phi_guard.pl --all` passes, any tests pass, and the code runs end to end on stand-in data.
  4. Get a fresh review from a separate agent that did not write the change, briefed with the goal and the files (not your conclusions), reading the diff against this file and the README. Fix what it finds, or note why not.
  5. Update the PR description to match the final scope, and only then say it's ready.

## This project

- **Data:** none. The package holds no data about people. Its only tables are published reference tables: the GLI-2012 and GLI Global spirometry splines (`data-raw/*.csv`, from the GLI workbooks; sources in `data-raw/README.md`) and `R/sysdata.rda`, built from them by `data-raw/build_sysdata.R`. `phi-guard.conf` allows those three files by exact path, and `DESCRIPTION` for the maintainer's email that CRAN requires. Users run these functions on their own cohort data (CARDIA, MESA and others): that data never comes here, not even as an example, a test case, or output pasted into an issue. No small-cell threshold is set.
- **Public repository:** everything committed is published. Examples, tests and vignettes use published worked examples or made-up values only, never rows from a real study, even rounded or perturbed.
- **Stand-in data:** the tests in `tests/testthat` use published reference values (Goff 2013 Table A, the preventr test suite, the GLI tables and the GLI implementation memo) and made-up inputs.
- **How to run:** `devtools::test()` and `devtools::check()`; rebuild `R/sysdata.rda` with `data-raw/build_sysdata.R` only when the source tables change. Lab-core files (`hooks/`, `tools/`, `AGENTS.md`, `CLAUDE.md`, `phi-guard.conf`, `.gitattributes`) are in `.Rbuildignore` so they stay out of the package.
- **Status:** v0.2.0 released (Zenodo DOI in the README). License stays GPL-3.0-only.
